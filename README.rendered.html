Note Publishing Suite（NPS）

書くところまで自動化。公開は、人が決める。

概要

ローカル素材から Note の下書きを作り、検査し、エディタへ反映する NPS（Note Publishing Suite） です。Codex / Claude Code から使えます。 公開・予約投稿・SNS 共有は自動で行わず、必ず公開直前で止まります。

パッケージ版: 0.3.12

キャラクター画像の参照・生成添付・出力・目視観察を同じ版へ束縛する検査は scripts/image_reference_gate.py を使います。画像設定は利用者側の既存記事profileへ置き、packageに個人の画像や名前を保存しません。

読書用プレビューは note_virtual_preview.py、編集診断は同コマンドの --diagnostics、由来レビューは note_preview.py --review-provenance を使います。原稿の本人確認・保留は検査で維持します。

使い方: NPS として使う（3分）

必要なものは POSIX sh、Python、git です。

1. 取る・確かめる

git clone https://github.com/nexus-ai-2045/note-publishing-suite.git
cd note-publishing-suite
sh scripts/verify_public_package.sh

Windows では PowerShell verifier も使えます。

pwsh -NoProfile -ExecutionPolicy Bypass -File scripts/verify_public_package.ps1

-ExecutionPolicy Bypass はこのプロセスだけに適用されます。 この verifier は Python と git も使って各 checker を実行するため、 先に利用可能か確認してください。 検証は公開操作を行わず、embedded copy と standalone clone の契約を確認します。 ローカル検証（verify:local）は上記の verifier で実行します。公開前の停止確認は python scripts/review_draft.py review-draft <draft> --json と python scripts/run_local_draft_qa_proof.py <draft> --output <workspace-output.json> --json で、対象原稿とpackage外の出力先を指定します。構成・安全境界・README表示・公開前停止線の確認範囲は開発・検証を参照してください。 自動テストのあとに行うユーザー受け入れ確認は USER_TEST.md の4ケースを使います。 受け入れテストの合格は Note 公開の承認ではなく、公開操作は別の人間承認で扱います。

2. 保存先を選び、Codex に登録する

初回はAIが、保存先・読んでよい素材・本人の文体参照を案内します。 既存の個別設定は使い直し、なければ初回設定の案内に沿ってpackage外のworkspaceへ保存します。画像・履歴・調査policyは用途に応じて選びます。

installerが行うのはpointer登録です。設定作成、Noteログイン、画像アップロードの対応確認まで完了するわけではありません。 例の ../my-note-workspace は先に作成し、自分の保存先へ置き換えてください。

installer は実体を複製せず、package を指す pointer だけを置きます。

pwsh -NoProfile -File adapters/codex/install.ps1 `
  -PackageRoot (Resolve-Path .) `
  -WorkspaceRoot (Resolve-Path ../my-note-workspace)

既定の配置先は $env:CODEX_HOME\skills、未設定なら $HOME\.codex\skills です。

macOS / LinuxのCodexは NOTE_SKILL_RUNTIME=codex bash adapters/claude-code/install.sh ../my-note-workspace、Claude Codeは bash adapters/claude-code/install.sh ../my-note-workspace を使います。

installerの終了時にも初回設定の案内先を表示します。Windowsの日本語案内はUTF-8で出力します。登録後の最初の依頼では「初回設定から案内して」と伝えてください。設定読戻しが失敗した場合は制作前に修正します。対話による案内であり、GUIの設定ウィザードはありません。

3. 最初の依頼例

Codex / Claude に、だいたい次のように頼むと NPS が起動しやすいです。

note-publishing-suite で進めて。

公開・予約・SNSはしない。下書き保存の手前まで。
やりたいこと言うこと（例）

下書き「候補1で note 下書きを作って」
検査「prepublish QA して」
エディタ反映「Note editor に反映。公開はしない」

固定の ネタ帳.md は使いません。入力は、ユーザーが最初に指定した 「読んでよい素材フォルダ」だけです。

公開済み記事を扉絵・本文だけ更新した場合は、元下書きを仮作成せず、verify_published_update.pyで公開APIの現在値を照合します。手順はpost-publish-context-proof.mdを参照してください。

下書き前には問答packetで本人の言葉、判断、避けたい断言、残したい脱線を確認し、 voice_profileとshortening_budgetを固定します。詳しくは note-draft-authority-and-layout-contract.md。

既存記事の起稿・修正前は、外部settingsから現在の文体参照本文と記事別の採否履歴を読みます。

python scripts/note_feedback.py --readback --settings USER_SETTINGS_PATH --article-id ARTICLE_ID --source SOURCE_SNAPSHOT --draft CURRENT_DRAFT

この入口は既存履歴と現稿の一致を検査して内容を返す読取り専用処理です。標準出力JSONをjson.loadsやConvertFrom-Jsonで復号してから、元の参照本文を読みます。書く担当は、受け取った内容を先に読み、適用・保全・保留した具体的な直しを返します。hash一致だけで意味の適切な反映を証明しません。本人が話していない体験・感情・判断で空きを埋めるテンプレートは使いません。詳しくは設定・読戻し契約を参照してください。

制約と安全設計

要点だけ先に:

1. 読んでよい素材は、ユーザーが指定したフォルダだけ 2. 公開・予約・SNS は明示承認なしに押さない 3. 根拠ラベル（本人の言葉 / 外部事実 / AI整理）を混ぜない

保証ラチェットでは、失敗の原因・復旧方法・次回の禁止事項を残し、再発防止できるものを既存の検査器・契約テストへ反映します。UI依存の手動境界と自動検査の限界は保証ラチェットの詳細にまとめています。

根拠ラベル・provenance（詳細）
  • 根拠は source_database / source_pack、構成案は series_plot、

    • article_plot、skeleton、wall_bang として分離します。

  • production_candidate と editor_fixture を混ぜません。詳しくは

    • note-article-provenance-design.md。

  • source_pack_locked_with_user_speech_priority では user-said、

    • external-fact、assistant-organized、hold を区別します。

  • 公開前に scripts/provenance_leak_check.py --scope changed を実行します。

    • 個別denylistは data/provenance_leak_policy.local.json に置き、 公開パッケージへ直書きしない設計です。

  • 公開、予約投稿、SNS共有、リポジトリ公開範囲変更は、対象・操作・方式の

    • いずれかが不明、または現在の会話で明示承認がない場合は実行しません。

根拠ラベルの確認:

python scripts/provenance_label_check.py <draft.md> --json

AI 作文を含む下書きは、次の順でローカルレビューします。

python scripts/provenance_label_check.py <draft.md> --json
python scripts/note_preview.py <draft.md> --review-provenance -o <review.html>
python scripts/provenance_label_check.py <draft.md> --public-output <public-body.md>
  • 「記事を書いて」「文章にまとめて」「会話を記事に」「メモを記事に」

    • 「下書きを直して」も下書き制作の自動発火対象です。

  • レビュー HTML は本人=緑、AIのつなぎ=黄、資料の事実=青、保留=赤で塊を色分けし、

    • 上に種類ごとの件数と本文の字数を出します。下書きの frontmatter は表示しません。

  • 修正対象は内部 ID ではなく、見出しまたは本文の短い引用で指定できます。
  • hold が残る間は公開本文候補を書き出しません。公開本文候補では

    • ローカル管理用の由来コメントを除去します。

Note エディタの詳しい境界

Note エディタの境界

接続できる場合に限り、タイトル、本文、リンク、画像、タグなどを反映します。 下書き保存までで止まり、公開・投稿・予約確定ボタンは押しません。

  • 低レベル操作: note-editor-ops
  • 公式機能の棚卸し: note-editor-capability-inventory.md
  • 1 cycle / 1 action: note-editor-pdca-orchestration.md
  • 実画面の制約: note-editor-live-constraint-boundaries.md
  • 画像アップロード停止線: note-image-upload-automation-boundary.md / scripts/note_image_upload_boundary_check.py
  • 公式情報: note-official-guidance-intake、制約調査: note-editor-constraint-debug

リンクカードはURLを単独行に置いて Enter を押し、figure[data-src] などの DOMで確認します。同期しない場合や固定座標が必要な場合は手動境界へ切り替えます。 Noteログイン、常時接続、画像アップロードの完全自動化は保証しません。

詳しい制作・開発手順

CIの repo-preflight は 11506e5eff12651f701752de2720fec769acd323 を固定参照します。引用符を含む入力で名義検査の走査を繰り返す問題に対応した版で、検知語彙・検査方針・権限は維持します。

対話を続けながら骨組みと全文を育てるでは、テーマごとの対話、複数記事、ローカルの全文編集画面、AI候補の選択反映、保存・取消し・再開を扱います。既存の外部workspaceと採否履歴を使い、公開操作は行いません。

ドキュメント同期・開発検証・制作と公開後の詳細を参照してください。毎回の開発検査は同じ文書に分けています。 基本の開発検証は python -m pytest scripts/test_skill_integration.py tests、文書確認は python scripts/docs_sync_check.py --base-ref origin/main です。

公開前観測は python scripts/note_editor_prepublish_verify.py data/note_editor_prepublish_observation.fixture.json --json、報告文は python scripts/japanese_closeout_language_check.py --json で検査します。 日本語報告の ready for review は下書き解除済み、open PR は未マージPR、MERGED はマージ済み、mergeable はマージ可能です。 これらを英語のまま報告した場合は構造バグとして出力ゲートを修正します。コマンド、ファイルパス、URL、SHA、識別子は原文のまま扱います。
